## 다이어그램의 구조·상호작용

페이지는 Browser / mini_React, HTTP Gateway, Mini Redis TCP/RESP, DBMS Bridge, DBMS SQL, DBMS 파일 저장 계층을 한 화면에 연결한다. 기본 테마는 다크 모드다. 필요하면 라이트 모드 전환을 제공한다.

v7의 데이터 지도 규칙을 따른다.

- 얇은 회색 실선 ①~⑱은 조사한 실제 소스 연결이며 항상 보인다.
- 현재 실행 단계의 데이터 경로는 굵은 색 선과 화살촉으로 강조한다.
- 현재 실행 중인 함수명은 분홍 글자로 표시한다.
- 각 화살표 라벨에는 이동 데이터와 동작을 짧게 쓴다. 선만 보고 의미를 추측하게 두지 않는다.
- 화살표 호버 시 색상 반응을 주고 클릭 시 중앙 정보창을 연다.
- 노드 상자와 각 텍스트 줄도 각각 클릭 가능해야 한다. 상자 전체의 일반 정보와 문장별 세부 정보가 중복 실행되지 않게 이벤트 전파를 관리한다.
- 세부창은 뷰포트 중앙에서 열리고, 긴 글은 내부 스크롤로 읽힌다. X 버튼, 배경 클릭, Escape 닫기를 제공한다.
- 포트는 원본과 대조해 표시한다. Gateway HTTP 3000, Mini Redis 6379, DBMS Bridge 6380, SQL 6381.
- 텍스트·카드·화살표 사이에 겹침이 없어야 한다. 긴 라벨, 좁은 창, 가로 스크롤도 확인한다. 연결선은 가능한 직교 경로로 배치한다.
- 겹침 검수는 [`FLOW_DIAGRAM_SKILL.md`의 3-1절](FLOW_DIAGRAM_SKILL.md)을 따른다. SVG를 실제로 렌더한 뒤 라벨 `getBBox()`와 상자·선의 좌표를 대조한다. 기준선 숫자만으로 통과시키지 않고 글자 경계와 상자 경계 사이의 실제 간격을 확인한다.
- 배경색 외곽선이나 투명 차폐판으로 겹친 선과 글자를 가린 것을 “겹침 없음”으로 판정하지 않는다. 우선 좌표 또는 문구 길이를 고치고, 화면에서 충돌이 0건인지 확인한다.
- 화살표 hover와 키보드 focus에서는 선 몸통과 화살촉이 같은 강조색으로 바뀌어야 한다. SVG `<marker>`는 별도 색상 요소로 확인하고 기본 marker와 강조 marker를 각각 검수한다.

## 모든 문장 상세창의 고정 형식

사용자가 제공한 붙여넣은 텍스트의 `항목 1`부터 `항목 18`까지의 레슨 문체를 따른다. 설명은 항목마다 아래 칸을 전부 가진다. 어떤 칸도 몇 개 대표 항목에만 넣지 않는다.

1. **항목 번호와 제목**: 모든 문장을 고유 번호로 식별한다.
2. **원문**: 지도에서 클릭한 정확한 한국어 문구를 표시한다. 원문 영어가 있을 때는 영문도 보존한다.
3. **직관적 1초 컷 독해**: 요구나 실행 의미를 학습자가 바로 이해할 수 있는 짧은 생각 문장으로 쓴다.
4. **바로 읽기**: 주체·대상·동작·방법을 실제 구현에 맞춰 설명한다.
5. **이 조건이 없으면 생기는 대참사**: 해당 처리 누락 시 가능한 구체적 실패를 설명한다. 관련 없는 일반 장애 문구를 재사용하거나 과장하지 않는다.
6. **예상**: 요구가 기대하는 설계 결과를 기술한다. 아직 구현·측정하지 않은 기대를 관측 사실로 바꾸지 않는다.
7. **반응**: 해당 코드를 읽을 때 다음으로 확인할 구현 질문이나 논점을 제시한다.
8. **의심**: 항목별 경계 사례·동시성·오류·한계에 관한 실제 검토 질문을 둔다.
9. **깨달음**: 이 코드가 시스템에서 맡는 책임이나 핵심 메커니즘을 설명한다.
10. **확인**: 근거 파일과 1-based 실제 줄 번호, 실제 실행한 테스트의 결과와 범위를 기록한다.
11. **뉘앙스 / 의역**: 위 설명을 되풀이하지 말고 공학적 의미를 새 문장으로 정리한다.
12. **핵심 로직 소스코드 · 줄별 주석**: 관련 원본 코드 줄을 보여 주고 모든 발췌 줄마다 바로 알아볼 수 있는 한국어 주석을 붙인다.

### 항목별 고유성 규칙

각 줄은 고유한 분석 데이터 레코드를 가진다. 모듈 수준 공통 문장을 `직관적 독해`, `대참사`, `예상`, `반응`, `의심`, `깨달음`, `확인`, `의역`에 반복 삽입하는 방식은 불허한다. `바로 읽기`만 문장별로 바꾸고 나머지를 공통 문구로 채우는 것도 불허한다.

각 레코드의 확인 방법은 그 문장의 동작을 실제로 검증하는 테스트 또는 소스 경로를 가리킨다. 같은 테스트 실행이 여러 문장을 포괄할 수는 있지만, 각 항목의 확인 설명은 해당 함수·분기·테스트 케이스와 연결해 쓴다. 해당 컴포넌트에 직접 실행 테스트가 없으면 소스 대조 사실과 미실행 범위를 구별한다.

### 영문 원문 병기와 중복 금지

영어 원문은 한국어 설명과 함께 표시한다. 영문만 단독으로 노출하지 않는다. 기술 식별자·함수명·프로토콜 토큰은 정확성을 위해 원형으로 유지하고 한국어 기능 설명을 덧붙인다.

예를 들어 `The WAL file stores transaction log records.`는 아래처럼 병기한다.

- 영문 문장: `The WAL file stores transaction log records.`
- WAL 파일에는 트랜잭션 로그 레코드를 기록해 변경 이력을 남긴다.

영어 원문과 해설은 같은 문장을 반복 출력하는 용도가 아니다. 한국어는 역할·결과·설계 의미를 설명한다. `select는 소켓의 읽기·쓰기 준비 상태를 기다립니다. 단일 이벤트 루프는 준비된 연결을 차례로 처리합니다.`처럼 같은 한국어 문장을 원문·바로 읽기·깨달음 등에 그대로 복제하지 않는다. 각 칸은 다른 질문에 답한다.

작성자가 새로 만든 영어 설명을 소스 주석이나 원저자의 원문인 것처럼 표시하지 않는다. 출처 성격이 불명확하면 `영문 설명`이라고 적는다. 관측하지 않은 O(1) 계측, 10,000 키 성능 측정, 성공률 100%, 데이터 복원 100% 같은 수치를 만들어 쓰지 않는다. 복잡도는 이론상 기대와 실제 관측을 구분한다.

## 핵심 로직 코드 발췌와 줄별 주석

코드 블록은 장식이 아니라 확인 가능한 근거다.

1. 각 문장의 관련 파일을 직접 열고, 팝업에 적은 줄의 실제 문자열을 복사한다. 함수명만 비슷한 의사 코드를 인용 코드처럼 넣지 않는다.
2. 각 발췌 행의 파일과 원본 줄 번호를 함께 제시한다. 여러 파일을 묶으면 파일 경계와 각 줄을 분리해 적는다.
3. 코드의 모든 줄마다 바로 아래 또는 인접한 `// 줄별 주석:`을 넣는다. 한 줄만 발췌했다면 그 한 줄의 주석이 왜 중요한지 설명한다. 두 줄 이상이면 주석 수도 비어 있지 않은 발췌 줄 수와 맞춘다.
4. 주석은 해당 줄의 실제 역할을 말한다. 선언은 입력과 반환 책임, 조건식은 참일 때 분기, 함수 호출은 넘기는 대상·인자, 반환은 전달되는 값, 해제는 소유 메모리, 파일 I/O는 기록량·오류 분기를 설명한다.
5. 주석을 덧붙인 화면용 발췌는 원본 수정 코드와 혼동하지 않게 `발췌 행`과 `줄별 주석`으로 구분한다. 주석을 붙였다고 원본을 수정하거나 주석이 원래 소스에 있었다고 주장하지 않는다.
6. 여러 줄 signature나 선택 발췌를 쓸 때도 실제 원본 행을 확인한다. 인용 코드가 연속하지 않으면 선택 발췌임을 밝히고 각 행의 원본 번호를 개별 표시한다.
7. `...`로 실제 로직을 생략한 코드를 완성된 핵심 코드처럼 내놓지 않는다. 생략해야 하면 발췌라는 점과 생략 범위를 밝힌다.
8. 발췌와 줄별 주석이 완성된 후 자동 검사로 각 `file:line`에 있는 원문이 팝업 코드와 일치하는지 확인한다.

## 자동 완성 검사

1. 모듈 카드 요소를 찾아 제목·본문 문구 수를 세고 팩트 레코드 수와 대조한다. 기대값은 8개 카드·34개 문장이다.
2. 해시와 TTL 강조 항목 레코드도 별도로 확인한다.
3. 각 문장 레코드가 10개 이상의 사용자 지정 분석 칸과 영어/한국어 병기 정보를 갖는지 확인한다. 문장에 따라 비어 있는 칸이 있으면 완료시키지 않는다.
4. 같은 카드 안에서 분석 필드 문자열을 비교해 동일한 문장이 여러 칸에 반복되는지 검사한다. 원문 반복이 의미상 필요한 경우에도 해설 문장을 새로 작성한다.
5. 발췌 코드의 `file:line`마다 실제 파일 줄과 동일한지 검사하고, 모든 코드 행의 줄별 주석이 존재하는지 검사한다.
6. 영문 설명문 전체를 검색해 한국어 설명이 옆에 있는지 확인한다. 자연어 문장 하나만 영어로 남기지 않는다. 영어 식별자는 한국어 기능 풀이와 함께 둔다.
7. `확인 필요`, 부정확 줄 번호 안내, 테스트 미실행 상투 문구, 미측정 수치가 남았는지 검색한다. 실제로 하지 않은 검증을 했다고 쓰지 않는다.
8. 인라인 `<script>`를 `.js` 임시 파일로 분리하여 `node --check`를 통과시킨다. JSON 인코딩 때문에 줄바꿈이나 따옴표가 JavaScript 문법을 깨지 않는지 확인한다.
9. 브라우저에서 다크 기본 테마, 전체 34 문장 클릭, 해시·TTL 클릭, 영어·한국어 병기, 줄별 코드 주석, 중앙 모달, 닫기/Escape, 화살표 hover/focus/click, 선·화살촉 동시 색 변화, 스테퍼 강조를 확인한다. 넓은 화면과 좁은 화면에서 글자·상자·선의 경계가 겹치거나 잘리는 곳이 0건인지 검사한다. 브라우저 화면을 보지 못했다면 정적 검사 통과와 화면 검수를 구분해 보고한다.
10. 임시 Docker build/test 산출물은 임시 폴더에 두고 원본 작업 트리는 보존한다.

## 최종 보고 형식

완료 보고는 생성·수정한 절대 경로를 연결해 제공한다. 주요 변경은 문장별 분석 범위와 줄별 주석 적용 여부를 요약한다. 실행한 테스트와 skip·미실행 범위, 성능 수치의 출처를 분리해 쓴다. 실제 확인되지 않은 기능이나 원본 영속성 보장을 단정하지 않는다.


## 화살표 정보창 전수 재구성 — 추가 필수 기준

화살표 ①~⑱도 문장별 상세창과 같은 형식을 적용한다. 노드 정보만 바꾸고 화살표의 기존 `연결 상세 / 근거 범위` 형식을 남기면 완료가 아니다. 각 화살표는 원문, 직관적 1초 컷 독해, 바로 읽기, 이 조건이 없으면 생기는 대참사, 예상, 반응, 의심, 깨달음, 확인, 뉘앙스 / 의역의 10칸과 실제 핵심 코드의 줄별 한국어 주석을 갖춘다.

1. 18개 화살표 ID와 상세 레코드 ID의 집합이 정확히 일치해야 한다. 각 연결마다 데이터, 호출자, 수신자, 실패 조건, 처리 순서를 따로 작성한다.
2. 연결 ⑦은 GET miss 후 캐시 채우기와 PUT 원본 우선 저장을 설명한다. SQL TTL 저장은 연결 ⑫와 구별한다.
3. 모든 코드 발췌는 현재 원본에서 직접 읽고 `파일:실제 행`을 표시한다. 줄마다 한국어 주석을 붙이며, 떨어진 행을 모은 경우 선택 발췌라는 점을 표시한다. 줄별 주석은 원본 주석과 구분한다.
4. `근거 범위`의 상투 문단은 반복하지 않는다. 해당 연결의 `확인` 칸에서 구체적 코드 위치와 실행 검증 범위를 밝힌다.
5. ⑰의 id 조회는 메모리 B+Tree와 테이블 행 파일의 관계를 설명한다. 이를 디스크 B+Tree/pager 경로로 추측해 바꾸지 않는다.
6. ⑱의 현재 SQL `execute_insert`는 테이블 행 쓰기와 메모리 인덱스 갱신 경로다. Bridge의 transaction/WAL 경로와 혼동하지 않는다. 소스에 없는 WAL 호출을 화살표 이름·본문·코드에 넣지 않는다.
7. 최종 검사에서는 18개 연결 모두가 동일한 구조의 중앙 모달로 열리고, 모든 발췌 행이 원본과 일치하며, 발췌 행 수와 한국어 주석 수가 같은지 확인한다. 영어 설명이 있으면 한국어 설명을 병기하고 설명 칸 사이의 동일 문장 반복을 제거한다.


## 모든 핵심 코드 발췌창의 가독성 기준

노드·문장·강조 문구·화살표의 코드 영역은 하나의 공통 렌더러로 표시한다. 긴 `파일:행 | 코드 // 주석` 문자열을 한 덩어리로 출력하는 방식은 사용하지 않는다.

- 같은 파일의 연속 발췌는 파일 경로를 상단 제목에 한 번 표시한다. 파일이 바뀔 때만 새로운 파일 제목을 만든다.
- 각 발췌 행은 독립 블록이다. 왼쪽에 원본 줄 번호, 오른쪽에 원문 코드를 배치하고, 그 아래에 설명 본문만 별도 영역으로 표시한다. 각 줄에 반복되는 설명용 제목이나 라벨은 붙이지 않는다.
- 코드 들여쓰기와 실제 개행을 보존한다. 코드가 길면 코드 영역만 가로 스크롤한다. 긴 경로와 한국어 설명은 줄바꿈한다.
- 코드 글자는 기본 13px, 행간 1.65 이상을 사용한다. 해설은 읽기 쉬운 본문 글꼴과 행간을 사용하고 코드와 색·여백으로 구별한다.
- 190px 높이의 작은 코드창에 코드와 주석을 함께 몰아넣지 않는다. 상세창 전체의 스크롤로 읽되 코드 영역의 가로 스크롤만 필요할 때 제공한다.
- 좁은 화면에서는 해설 영역을 왼쪽으로 확장해 읽기 폭을 확보한다. 파일 경로와 해설이 코드 열에 겹치지 않게 한다.
- 구조화된 코드 자료는 원문·줄 번호·주석을 별도 필드로 전달한다. 화면 문자열을 다시 파싱해 원문을 추정하지 않는다. 기존 일반 코드 발췌도 공통 렌더러로 표시하되 확인되지 않은 줄 번호나 해설을 만들지 않는다.
- HTML 삽입 문자열 대신 textContent로 원문과 해설을 채운다. 코드의 꺾쇠와 따옴표가 문법 강조나 HTML 요소로 해석되어 사라지면 안 된다.
- 검수 시 34개 문장, 해시·TTL 강조 경로, 18개 화살표, 일반 모듈 및 단계 노드의 코드 표시 경로를 전수 확인한다. 코드가 있는 모든 진입점이 같은 렌더러를 사용하는지 검사한다.


## 항목 18의 해시 테이블 코드 근거

`16 버킷 · 체이닝 · 키 비교`는 한 줄 해시식만 보여 주지 않는다. 직접 구현한 Node와 buckets 배열, 초기화, 버킷 계산, 기존 키 갱신, 새 충돌 노드 연결, 조회의 strcmp/next 순회를 여섯 코드 구간으로 보여 준다. 모든 발췌 행에 원본 행 번호와 개별 해설을 붙인다. 선택 발췌에서 빠진 오류 처리와 만료 분기는 생략 범위를 설명한다.

현재 원본은 C 구조체와 고정 버킷 배열을 손수 구현한 분리 체이닝이다. 내장 해시 맵 호출이나 개방 주소법 슬롯 탐사는 구현하지 않았다. 이 판정은 Node.next, buckets[index], malloc, strcmp 및 head 삽입 코드로 근거를 제시한다. a와 q가 모두 버킷 1에 들어가는 계산 예시는 코드에서 도출한 사례로 표시하며 실행 실측이라고 쓰지 않는다. 이전 노드를 기록하는 previous = node와 다음 후보로 이동하는 node = node->next의 의미를 혼동하지 않는다. 고정 16버킷의 체인 증가와 키 문자열 비교 비용을 포함해 성능 한계를 설명한다.

### 코드 설명의 반복 라벨 제거

- 코드 아래에는 해당 줄의 설명 본문을 직접 표시한다. 설명 앞에 공통 제목·라벨을 반복 생성하지 않는다.
- 제거 대상은 표시용 라벨뿐이다. 한국어 설명 본문, 영어 원문 병기, 원본 코드, 파일 경로와 줄 번호는 유지한다.
- 공통 코드 렌더러를 확인해 박스·문장·화살표 상세에 같은 규칙을 적용한다. 사용하지 않는 라벨 전용 스타일도 제거한다.
- 검사 시 반복 라벨이 생성되지 않는지와 줄별 설명 본문이 그대로 남는지를 함께 확인한다.
